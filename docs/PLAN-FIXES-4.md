## 1. 手动下载的歌，从歌单播放仍走网络缓存

### 现状

- 手动下载写到 `Documents/downloads/<歌单名>/`，旁边有 `.json` sidecar（含 `source` / `sourceId`）
- 播放取流走 `resolveSource()`：先查**播放缓存**（`musicCache/` + `cacheIndexStore`），再走网络
- 两条链路完全独立：`downloads/` 里的文件**不参与**播放取流

所以从歌单点一首已下载的歌，`isCached()` 查不到（缓存索引里没有），就去网络取流并重新写 `musicCache/`。

### 取流优先级（改后）

```
1. 曲目自带 file://（下载页试听、导入本地）      ← 不变
2. 手动下载（downloads/ 索引命中）              ← 新增
3. 末段预取地址（仅当没有本地文件）
4. 播放缓存（musicCache/）
5. 网络取流
```

### 索引设计

`src/jk/downloadIndex.ts`：

- 键：`<source>:<sourceId>`（下载时 sidecar 里已写入）
- 值：`{ uri, quality, mtime, size }`；同一首歌有多份时按 **flac > 320k > 128k**，同档取最新
- 构建：首次使用时后台扫描一次 `downloads/`（读每个 `.json`），结果持久化到 MMKV
  - 下次启动直接读 MMKV，不扫盘
  - 下载完成 / 删除下载时增量更新并落盘
  - 扫描未完成时播放不等待，直接走后面的缓存/网络
- 校验：命中后 `getInfoAsync` 确认存在且 size > 0；失败则从索引剔除并继续往下走

### 边界情况

| 情况 | 行为 |
|---|---|
| 没有手动下载 | 走原来的顺序：预取 → 缓存 → 网络 |
| 已有播放缓存、没下载 | 用缓存（和现在一致） |
| 既有下载又有缓存 | **下载优先**（用户主动下载的，通常是更高音质） |
| 下载文件被系统/用户删掉 | 索引校验失败 → 剔除 → 回退缓存/网络，不报错 |
| 下载的是 128k，现在设置是 flac | 仍用下载（本地可用优先）；想在线听可删掉下载 |
| 同一首歌下载过多份 | 按音质排序取最好，同档取最新 |
| 老下载没有 source/sourceId | 跳过（不按歌名猜，避免放错歌） |
| 下载后换源播放过 | 索引键是曲目原始 platform:id，不受换源影响 |
| 缓存 LRU 淘汰 | 不碰 `downloads/`，下载不受影响 |
| 重装 App | 索引从 sidecar 重建（下载文件在 Documents，保留） |
| 扫描耗时 | 只读 sidecar JSON，后台线程；不阻塞起播 |

### 影响面

- 只改取流顺序，不改播放器；下载过的歌起播更快、离线可播
- 风险：索引过期（用户手动删文件）→ 命中后先 `getInfoAsync` 校验存在与 size，失败则回退网络

### 验收

- 下载一首歌 → 到歌单里播放 → 日志出现 `[play] 使用下载文件`，`item0.url` 是 `file://.../downloads/...`
- 断网后从歌单播放已下载歌曲 → 正常出声
- 删除下载 → 再播放 → 走网络

## 2. 设置页文字颜色不跟随「文字颜色」

### 根因

- `macPalette()` 会读 `getTextColor()`，逻辑本身是对的
- 但设置首页、音源管理页只用了 `useAppTheme()`，**没有订阅 `textColorStore`**
- `useAppTheme()` 也不订阅 `textColorStore`
- 结果：改完颜色后当前页不重渲染，必须退出再进（重新挂载）才变色

实测：在基本设置里把颜色改成 `#FF3B30` / `#00C853`，标题与行文字变红/绿；但同一页面里其他分区、设置首页、音源管理页要重新进入才变。

### 方案

1. `useAppTheme()` 里订阅 `textColorStore.useValue()`（一行），让所有用 `useAppTheme()` 的页面在改色时重渲染
2. 顺带订阅 `accentStore` / `wallpaperStore`（如果还没订阅），避免「强调色/壁纸改了当前页不刷新」的同类问题
3. 不改 `macPalette` 的取色逻辑（它已经是正确的单一来源）

### 影响面

- 只是多一次订阅，重渲染范围 = 使用 `useAppTheme` 的组件（本来就是主题消费者）
- 风险：订阅后 `useAppTheme` 返回值若每次新建对象可能引起多余重渲染；实现时保持 useMemo，依赖里加 textColor

### 验收

- 基本设置里改文字颜色 → 标题、行文字、hint 立即变色（不退出页面）
- 返回设置首页 → 颜色已同步
- 播放页、歌单页、音源管理页同样立即生效

## 3. 音源测试通过，播放时仍换源

### 现状（1.4.53 已改进一半）

现在的测试是：拿「稻香 / 周杰伦」搜一次 → 取地址 → Range 拉 32KB 校验。

它能说明的是：**这个音源的接口在这个平台上能搜到、能取到、能拉到数据**。
它不能说明的是：**你正在播的那首歌，这个平台有没有版权/能不能取到完整地址**。

换源的真实触发条件（`failToPlay`）：

| 触发 | 说明 |
|---|---|
| 取流失败 / 地址为空 | 平台接口报错、限流、无版权 |
| 起播看门狗 12s 没进度 | 地址拿到了但 AVPlayer 拉不动 |
| 播放中停滞 15s | 播着播着断了 |
| 试听片段判定 | 实际时长明显短于标称（30/60 秒整） |
| 换源后仍失败 | 继续换下一个平台，最多 5 个 |

所以「测试 ✓ 但播放换源」通常不是测试坏了，而是**那首歌在该平台不可用**——但用户看不到这个区别，体验上就是「测试骗人」。

### 测试设计（3 首样本）

**样本怎么选**：不用固定歌名去撞版权，而是**每个平台用自己搜索到的结果**：

1. 用 3 个不同年代的查询词（不是固定曲目）：
   - `稻香 周杰伦`（华语老歌）
   - `起风了 买辣椒也用券`（近年热歌）
   - `Shape of You Ed Sheeran`（欧美）
2. 每个平台对每个查询词取**该平台搜索结果的第 1 条**，再取流 + Range 拉 32KB
3. 这样「歌在平台搜得到」= 平台有这个版权；取流失败才是真的不能播（VIP/试听/接口坏）

**结果怎么显示**：

- 每平台 `x/3`：`tx 3/3`、`kg 2/3`（第 3 首失败：无版权）
- 失败时带上第几首与原因：`kg 2/3 · Shape of You: http 403`
- 3 首全超时 → 显示「网络异常」而不是「平台不可用」

**耗时 / 流量**：

- 每个平台串行跑 3 首，5 个平台并发 → 最坏约 20–25s
- 每首只拉 32KB → 全平台合计约 480KB
- 有进度条（`kw 1/3…`），可随时取消（取消后不再发新请求）

**缓存清理**：

- 测试只调 `getMusicUrl` + `fetch(Range)`，**不写** `musicCache/`，也不触发自动缓存
- 测试期间不切换当前音源（`isSelected` 不落盘），测完不影响正在播的歌
- 若某些脚本内部有缓存，属于脚本自己的内存缓存，不落盘

**不打扰播放**：

- 测试并发上限 5（每平台 1 个），不占用播放取流的脚本池
- 测试期间禁止触发 `preload` / `maybeCacheCurrent`

### 影响面

- 测试耗时从 ~15s 变成 ~30s（3 首并发）
- 换源逻辑不变，只是把原因透出来

### 验收

- 测试显示 `3/3` 的平台，播该平台的热门歌基本不换源
- 测试显示 `1/3` 的平台，播放时换源能看到具体原因
- 诊断页能对上「哪首歌、哪个平台、什么原因」

## 4. 实时活动中断 / 控制中心丢控制

### 现象拆解

**4a. 进度不更新**

- 灵动岛/锁屏卡片里的进度条是**静态值**：`ProgressLine(progress: context.state.progress)`
- 进度只靠 JS 每 2 秒 `updateLiveActivity()` 推一次
- App 进入后台被挂起（或系统限流）后 JS 不再推送 → 进度条冻住、剩余时间不动

**4b. 从抖音切回来，控制中心显示「未在播放」**

- 抖音播放时，系统的「正在播放」App 切换到抖音；我们的 `MPNowPlayingInfoCenter` 条目被顶掉
- 抖音退出后，我们如果处于**暂停**状态（中断时 RNTP 会 pause），没有新的状态变化 → 不会重新 publish
- 我们也从不设置 `MPNowPlayingInfoCenter.default().playbackState`
- 结果：控制中心既没有抖音（已停），也没有我们（没重新发布）→「未在播放」

**4c. 实时活动「中断」**

- 原生 `CyMusicLiveActivityModule` 用 `static var activity` 记录当前活动
- App 被杀/重启后这个静态变量是 nil：
  - `update()` 直接 return（进度永远不动）
  - `start()` 时 `endInternal()` 也找不到旧活动 → 旧卡片残留在锁屏
- 没有 `staleDate`，系统不会自动把过期卡片收掉

### 参考：QQ 音乐 / 酷狗 / 网易云的做法

- **Now Playing**：播放/暂停/切歌都写 `MPNowPlayingInfoCenter`，并且**显式设置 `playbackState`**；
  回到前台、音频会话重新激活时**再 publish 一次**；中断结束后按 `shouldResume` 恢复并重新激活会话
- **实时活动**：进度用 `ProgressView(timerInterval:)` / `Text(timerInterval:)` 交给系统自己走，
  App 只在「播放/暂停/切歌」时更新状态；`staleDate` 兜底；启动时 `Activity.activities` 接管残留活动
- **媒体服务重置**：监听 `AVAudioSession.mediaServicesWereResetNotification`，重建播放器

### 方案（按你的要求：不用系统计时、保留现有进度与紫色描边、封面换软件图标）

**A. 灵动岛 / 锁屏卡片（软件自己的实时活动）**

1. **封面改成 App 图标**：把图标资源放进 Widget Extension 的 asset catalog，`ArtworkView` 改成显示图标；
   不再把歌曲封面压成 base64 塞进 attributes（顺带解决 4KB 上限和编码耗时）
2. **保留现有进度条与倒计时**：`ProgressLine` + `remainingText` 不动，仍由 App 更新
3. **保留紫色边缘细线**：`activitySystemActionForegroundColor` 与灵动岛 `keylineTint` 保持主题紫
4. 进度更新策略：保留 2 秒一次的更新，但只在「播放中」推送；暂停/切歌/seek 立即推一次
5. `staleDate = now + 30 分钟`：App 被系统杀掉后卡片不会永远停在一个错误进度

**B. 实时活动生命周期（原生桥）**

1. 模块初始化 / `start` 时先遍历 `Activity<...>.activities`：
   - 同一首歌 → 接管（`Self.activity = it`）
   - 不是同一首 / 已结束 → `end` 掉
2. `update` 时 `Self.activity == nil` → 从 `activities` 里找回，找回失败则重新 `start`
3. `end` 结束所有残留活动

**C. 系统「正在播放」（控制中心 / 锁屏系统控件）**

> 这部分和实时活动无关，是 iOS 的 Now Playing，必须让系统能读到歌曲

1. RNTP fork 增加 `refreshNowPlaying()`：
   - 重新写一次 `MPNowPlayingInfoCenter.nowPlayingInfo`（当前曲目 + 时长 + 进度 + rate）
   - 显式设置 `MPNowPlayingInfoCenter.default().playbackState = isPlaying ? .playing : .paused`
2. 触发时机：
   - `AppState` 变为 `active`（从抖音切回来）
   - 音频中断 `.ended`
   - `play()` / `pause()` / 切歌 / seek
   - `AVAudioSession.routeChangeNotification`（耳机拔插）
3. 中断结束：`shouldResume` 为真则恢复播放；为假也重新 publish，保证控制中心仍有我们的卡片（带播放按钮）
4. 监听 `mediaServicesWereResetNotification`：重建播放器 + 重新 publish

### 影响面

- 只动「系统层展示」，不动播放主链路
- 风险：实时活动状态结构变更 → Widget 与主 App 必须同时更新（同一个包，没问题）
- 风险：`playbackState` 设置不当会让控制中心按钮状态错乱 → 只按实际播放状态写

### 验收

1. 播放中锁屏 → 灵动岛/锁屏卡片：**App 图标** + 歌名 + 进度 + 倒计时，紫色描边保留
2. 播放中打开抖音播放 10s → 退出抖音 → 控制中心重新出现我们的歌，可暂停/下一首
3. 暂停状态下切到抖音再回来 → 控制中心仍显示我们的歌（带播放按钮）
4. 杀进程重开 → 锁屏卡片被接管（同一首）或清掉，不会残留旧进度
5. 耳机拔出 → 暂停且控制中心状态正确

## 已确认（2026-11-24）

1. **下载优先**：手动下载优先本地；没有下载的走原顺序（预取 → 缓存 → 网络）；
   下载被删/文件缺失自动回退，不报错；同曲多份按音质取最好
2. **音源测试**：跑 3 首样本，用各平台自己的搜索结果（避免「无版权」误判）；
   显示 `x/3` 与失败原因；不写缓存、不切当前音源、不占播放脚本池
3. **播放诊断**：设置 → 其他 → 播放诊断（最近 50 次换源与原因）
4. **实时活动**：不用系统计时；保留现有进度条与倒计时；封面改成 App 图标；
   保留紫色描边；另外修系统 Now Playing（控制中心/锁屏系统控件）
